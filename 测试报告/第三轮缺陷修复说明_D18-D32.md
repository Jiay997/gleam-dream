## 逐项修复说明

### D18（严重）— 资产 planning 状态前端禁用生成

- **原因**：前端 [CharacterDetailView.vue](../frontend/src/views/CharacterDetailView.vue) 的 `canGenerate` 计算属性遗漏 `planning` 状态，而后端 [asset_service.py](../backend/app/services/asset_service.py) 的 `_GENERATABLE_STATUSES` 白名单包含 planning——前后端状态机不一致，智能规划产出的资产在 UI 上无法发起视觉稿生成，关口二流程被阻塞。
- **修改**：`canGenerate` 补入 `planning`，并更新注释说明与后端白名单对齐。
- **验证**：Vite 编译通过（模块 HTTP 200 且产物含 planning 分支）；逻辑与后端 `_GENERATABLE_STATUSES` 逐值对照一致。

### D19（严重）— 跨服务重启后 HITL resume 失效

- **原因**：剧本审批 resume 依赖**进程内**后台任务消费 LangGraph checkpoint；服务重启后任务丢失，审批单虽已 approved 但状态推进/结算不再发生，项目永久卡在 script_review（旧进程无日志难以取证）。
- **修改**：[orchestration_service.py](../backend/app/services/orchestration_service.py) 新增 `reconcile_orphan_approvals()`，服务启动时（[main.py](../backend/app/main.py) lifespan 后台任务）扫描「已决策 + 领域状态未跟进」的孤儿审批单：
  - `script + approved + 项目 script_review` → 推进 asset_preparing，未释放冻结积分全额退还（结算数据随旧进程丢失，按失败兜底语义返还，不亏欠用户）；
  - `final_cut + approved + 项目 final_review` → 时间线置 approved 并推进 completed。
- **验证**：重启后日志 `孤儿审批单补偿完成 count=2`；API 实测项目 165 状态 = asset_preparing（原卡死 script_review）。

### D22（严重）— 全局 SSE 端点 404

- **原因**：前端 AppShell 订阅 `/api/v1/events/stream`，后端从未实现该路由（404），实时事件推送完全不可用，全部降级为轮询。
- **修改**：新建 [api/events.py](../backend/app/api/events.py)：
  - `GET /api/v1/events/stream`：聚合订阅当前用户**全部可见项目**（Owner + 成员）的事件流，多项目泵任务合并队列、按事件序号去重、15s 心跳、`Last-Event-ID` 断线补偿；
  - 认证复用 `get_current_user`（支持 `?access_token=` 查询参数，EventSource 无法自定义请求头）；
  - 在 [api/__init__.py](../backend/app/api/__init__.py) 注册路由。
- **验证**：原始 socket 探测返回 `HTTP/1.1 200 OK | text/event-stream; charset=utf-8`。

### D23（一般）— 事件流 query token 认证 401

- **原因**：项目级 SSE 端点（[projects.py L486](../backend/app/api/projects.py#L486)）依赖 `project_guard → get_current_user`，部分前端视图（分镜画布）订阅时**未携带** `access_token` 查询参数导致 20001；分镜画布视图漏带 token。
- **修改**：[StoryboardCanvasView.vue](../frontend/src/views/StoryboardCanvasView.vue) 的 SSE URL 补上 `?access_token=`（与资产墙/角色详情视图既有写法一致）；AppShell 全局流同步补带。
- **验证**：`GET /api/v1/projects/352/events?access_token=<有效token>` 实测 200（修复前 401）。

### D24（轻微）— 分镜生成完成后画布不刷新

- **原因**：受理后置 `generating=true`，刷新依赖 SSE 的 `storyboard.generated` 事件；SSE 不可用时降级轮询回调里 `generating=true` 直接跳过刷新——事件丢失 + 轮询不兜底 = 画布停在 0 镜空态。
- **修改**：`onPoll` 在生成中改为调用新增的 `pollGenerationResult()`（查分镜板列表，当前集出现分镜板即退出生成态并刷新详情）；SSE URL 补 token（见 D23）。
- **验证**：Vite 编译通过；轮询兜底路径与既有 `finishGeneration`/`loadCurrentDetail` 复用，逻辑静态审查确认。

### D26（严重）— 后期页首屏「时间线不存在」

- **原因**：`get_timeline_view` 仅查询不创建，而时间线只在 TTS/字幕/合成等动作 API 中惰性创建——用户首次进入后期页必然报错，且页面无创建入口（合成按钮在错误态下无响应）。
- **修改**：[post_service.py](../backend/app/services/post_service.py) 新增 `_ensure_preview_timeline_with_video()`：预览时间线不存在时按 P5 锁定镜头布局自动创建并装配 video 轨（与 compose 装配口径一致）；`get_timeline_view` 对 preview 走惰性初始化，master 缺失仍返回明确错误（前端展示未合成空态）。
- **验证**：修复后对 352 执行 compose（HTTP 202）→ final_review 全链路通过（compose 依赖同一装配逻辑）。

### D27（一般）— 母版时间线从未创建

- **原因**：`compose` 只处理 preview 时间线，母版（master）行永远不存在，后期页「母版」tab 永远为空。
- **修改**：`_run_compose_pipeline` 成功分支同步创建/更新 master 时间线（复制 preview 的时长/帧率/分辨率与全部四轨片段，status 跟随 pending_review）。
- **验证**：实测 compose 后 `GET /post/timeline?cut_type=master` 返回 timeline（pending_review）；关口四 approve 后变 approved。

### D28（严重）— 项目状态机后 4 态不可达

- **原因**：状态机定义了 rendering/post_producing/final_review/completed，但全代码无任何触发点：渲染发起不推进、合成提交终审不推进、终审通过不推进。
- **修改**（三处钩子）：
  1. [render.py](../backend/app/api/render.py) `batch_submit_render`：渲染批次受理（非幂等命中）且项目处于 storyboard_review 时推进 **rendering**；
  2. [post_service.py](../backend/app/services/post_service.py) `_run_compose_pipeline`：QC 通过提交终审时，项目处于 post_producing 则推进 **final_review**（compose 同步阶段已有 rendering→post_producing）；
  3. [orchestration_service.py](../backend/app/services/orchestration_service.py) `_finalize_gate_decision`：final_cut approve 且项目 final_review 时推进 **completed**。
- **验证**：对 352 实测全链：渲染受理 → rendering → compose → post_producing → 管线完成 → final_review → approve → **completed**（状态逐段取证）。

### D30（严重）— 关口四审批后导出被永久拦截

- **原因**：final_cut 审批单不属于剧本子图 interrupt，`resume_from_approval` 统一走剧本图 checkpoint resume——对 final_cut 无效果，时间线状态永远停在 pending_review，导出守卫「时间线尚未审批通过」永久拦截。
- **修改**：`resume_from_approval` 按 `approval_type` 分派：script 走原 checkpoint resume；storyboard/final_cut 走新增 `_finalize_gate_decision`（final_cut：approve → preview/master 时间线置 approved + 项目 completed，reject → 时间线打回 draft + 项目回 post_producing；storyboard：reject → 分镜/镜头解锁 + 项目回 storyboarding）；同时补 GATE_STORYBOARD/GATE_MASTER 埋点。
- **验证**：实测 approve final_cut #107 → master timeline approved → `POST /exports`（720p）成功创建导出任务 id=56（修复前同请求被 40001 拦截）。

### D31（严重）— V4 续写同步阻塞 83 秒 + 弹窗集数错误

- **原因**：
  1. `continue_script` 在请求线程内同步调用 LLM（实测 83 秒，含 JSON 解析失败自动重试），前端 fetch 超时 ERR_ABORTED，无进度无反馈，用户可能重复提交；
  2. 前端 [ScriptV4Panel.vue](../frontend/src/components/v4/ScriptV4Panel.vue) 的集数提示依赖父组件 `episodeCount` prop，而 [V4CapabilityView.vue](../frontend/src/views/V4CapabilityView.vue) 初始化为 0 后从未赋值——弹窗显示「当前 0 集」。
- **修改**：
  - 后端 [scripts.py](../backend/app/api/scripts.py) 续写端点改为 **202 后台受理**（[script_service.py](../backend/app/services/script_service.py) 新增 `spawn_continue_script`：独立短会话后台执行，完成发布 `script.continued` 事件、失败发布 `script.continue_failed`），返回当前版本/集数基线；
  - 前端 `continueScript` 类型更新；提交后 toast 受理提示 + 每 5 秒轮询版本列表（上限 3 分钟），出现更高 version_no 即成功提示并刷新；
  - 面板新增 `currentEpisodeCount` 计算属性：prop 缺省时从版本列表最新版本的 `total_episodes` 兜底。
- **验证**：实测续写返回 `HTTP 202 {"status":"accepted","current_version":3,"current_episodes":13,...}`（立即响应，不再阻塞）。

### D32（致命，回归中新发现）— 剧本新版本级联删除分镜成果

- **发现过程**：D31 回归验证执行续写后，storyboard #90 与 12 个镜头（含渲染成果）从数据库消失。
- **原因**：[script_service.py](../backend/app/services/script_service.py) `_rebuild_working_copy` 删除父版本 episodes 行，而 `storyboards.episode_id` / `shots.episode_id` 外键为 `ondelete="CASCADE"` → 任何产生新剧本版本的操作（续写/扩写/版本恢复）都会**级联删除已生成的分镜板、镜头与渲染关联**。同时 `_create_new_version` 从不更新 `project.current_script_id`，导致新版本创建后按 current_script_id 解析分集的路径报「集号 1 不存在」。
- **修改**（三处）：
  1. `_rebuild_working_copy`：删除 episodes 前先把旧 episode 上的 storyboards/shots **重挂到同集号的新 episode**（UPDATE episode_id），再删旧行（此时 CASCADE 无害）；
  2. `_create_new_version`：新版本创建后同步 `project.current_script_id = new_script.id`（旧值指向旧版本时）；
  3. `storyboard_service.generate`：集号解析增加兜底——当前版本缺该集时回退到含该集的最新版本（兼容历史脏数据）。
  - 配套：`compose` 的 video 轨有效性判定改为「片段数量与当前锁定镜头布局一致」，镜头集合变化后自动重铺，防失效 clips 残留。
- **验证**：修复后对 352 重建分镜（storyboard 91 / 12 镜）→ 绑锚点 → 锁定 → 渲染 12/12 → compose → 关口四 approve → 导出，全链路成功；分镜在续写场景下的存续由迁移逻辑保证（日志 `工作副本重建：分镜成果已迁移`）。
