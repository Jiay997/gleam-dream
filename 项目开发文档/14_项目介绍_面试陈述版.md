## 〇、精简版

> 浮光造梦是一个面向短剧创作者的 AI 全流程创作工具：**从一句话创意出发，自动完成剧本、角色资产、分镜、视频、配音配乐字幕、成片导出与分发**，把"一部短剧"的生产从"多人协作数周"压缩到"单人操作数小时"。
> 我独立完成了产品定义、系统架构和前后端实现：后端 FastAPI + LangGraph 多智能体编排，前端 Vue 3 + Konva 画布，57 张表、109 个接口、24 个页面，77 个自动化用例和 12 步端到端冒烟全绿。
> 它真正的差异点不在"能生成"，而在**把叙事确认放在最便宜的环节**——四道人工确认关口 + 冻结式计费，让用户"先看对，再花钱"。

## 二、目标用户：三类人，一个共同处境

短剧生产的真实结构是"重流程、轻创意"：一个点子要经过剧本、角色、分镜、成片四道翻译，每一道都由不同角色手工承接。

| 画像 | 代号 | 特征 | 核心诉求 | 付费意愿 |
|---|---|---|---|---|
| 个人创作者 | P-独立 | 1 人兼职/自由职业，月产 2–10 集，无固定团队 | 少花钱、少返工、全流程不切换工具 | 中（订阅 + 按量积分） |
| 小型工作室 | P-工作室 | 3–10 人，有编剧/剪辑分工，月产 30–100 集 | 角色一致性、协作、成本可预测 | 高（团队版） |
| MCN / 内容运营 | P-运营 | 矩阵号批量运营，月产 100+ 集 | 批量生产、模板化、一键分发 | 高（按量） |

**明确不服务（本期非目标）**：影视级长剧团队、数字人直播/实时换脸、私有化部署机构客户。理由分别是：产品复杂度不在同一量级、合规风险高且链路不同、与 SaaS 商业模式冲突。

> 讲这一页的目的不是背画像，而是让面试官看到**我先划边界再谈功能**。

## 三、核心问题与痛点：六个具体卡点

这是整个项目的立论基础。"AI 能生成"早就成立，卡住用户的是下面六件事：

| 编号 | 痛点 | 谁受影响 | 现状替代方案 | 为什么不够 |
|---|---|---|---|---|
| PB-1 | 剧本到分镜的"翻译"高度依赖人工经验 | 编剧、导演、制片 | 人工写分镜表、口头交代 | 产能瓶颈，一集 2 分钟短剧分镜耗时 2–4 小时 |
| PB-2 | AI 生成内容**角色不一致** | 所有 AI 工具使用者 | 反复重抽、垫图、训 LoRA | 一致性靠概率，跨镜头漂移明显，返工成本高 |
| PB-3 | 工具链割裂 | 个人创作者 | 剧本 A、图像 B、视频 C、配音 D、剪辑 E | 文件手工搬运，资产与元数据无法复用 |
| PB-4 | 生成成本不可控 | 付费创作者 | 逐次试错，先花钱再看结果 | 叙事错误在"视频生成"这个最贵环节才暴露 |
| PB-5 | 长流程中断即前功尽弃 | 所有使用者 | 从头再来 | 缺断点续跑与状态持久化 |
| PB-6 | 合规风险不自知 | 面向平台分发者 | 上传后被拦截或封号 | 缺前置审核与授权留痕 |

**痛点 → 方案 → 可验证指标**（这张表的对应关系是我做产品设计的核心逻辑）：

| 痛点 | 解决方案 | 观测指标（PRD 定义） |
|---|---|---|
| PB-1 分镜靠经验 | 导演 Agent 拆镜（镜头类型/景别/运镜/时长字段齐全）+ 画布拖拽重排 | 分镜时长约束 `duration_ms ∈ [1000,15000]` 落库级校验 |
| PB-2 角色漂移 | **资产锚点**：主形象 + 三视图 + 表情集锁定 `asset_id`，渲染以锚点为条件；QC 闭环 0.80 通过 / 0.68–0.80 警告并重抽（≤3 轮） | 跨 50 镜头质检通过率 ≥ 95% |
| PB-3 工具割裂 | 一条流水线八段式，资产与元数据在同一项目内复用 | 北极星 CCCR（创意→成片完成率） |
| PB-4 成本失控 | **草稿模式**：先出低成本静帧样片确认叙事，再进正式渲染（成本口径 ≤ 正式 15%） | 成本预估偏差 ≤ 15% |
| PB-5 中断重来 | 剧本链路 LangGraph checkpoint 断点续跑 + 全链路幂等键 | 断点恢复成功率 100% |
| PB-6 合规风险 | 生成前剧本前置审核（block 级终止）、真人授权四步留痕、成片强制 AI 标识 | 审核拦截流失率 ≤ 3% |

## 四、产品形态：八段流水线 + 四道人工关口

```
一句话创意
  → ① 剧本（一句话生成 / 小说解析 / 分集 / 局部改写 / 前置审核）
  → ② 资产（角色·场景·道具规划 → 主形象/三视图/表情集 → 一致性质检 → 锁定）
  → ③ 分镜（导演 Agent 拆镜 → Konva 画布拖拽排序 → 草稿预览 → 锁定）
  → ④ 视频（批量生成 → 队列/路由 → QC 闭环 → 失败重试与返还）
  → ⑤ 后期（TTS 配音 → 字幕对齐 → BGM → 混音 → 合成）
  → ⑥ 导出分发（母版导出 / 权益校验 / 元数据生成 / 一键分发）
  → 成片
        ▲ 计费与项目底座贯穿全程：冻结-结算-返还、14 态状态机、快照、审计、埋点
```

**四道 HITL（Human-in-the-loop）关口**是本产品的产品哲学所在：

| 关口 | 位置 | 用户决策 | 经济意义 |
|---|---|---|---|
| 关口一 | 剧本确认 | 通过 / 驳回（反馈 ≥10 字回流重写）/ 直接编辑 | 最便宜的纠错点 |
| 关口二 | 资产确认 | 主形象与三视图是否可用 | 一致性锚点在此确定 |
| 关口三 | 分镜锁定 | 镜头序列与草稿样片是否成立 | 决定最贵环节的输入 |
| 关口四 | 成片确认 | 配音/字幕/配乐是否达标 | 交付前最后一道闸 |

**一句话总结产品逻辑**：AI 负责"生产"，人只在四个**杠杆最高**的位置做判断；每一次判断都发生在下一阶段成本跃升之前。

| 技术 | 承担什么 | 为什么选它 |
|---|---|---|
| LangGraph | 编剧链路图编排：冻结预检 → 大纲 → 逐集生成 → 审核 → 审批 → 挂起/恢复 | 这是唯一"长程 + 多 Agent + 需断点续跑"的链路，图 + checkpoint 的收益最高 |

## 六、五个关键设计决策（体现判断力，建议重点讲）

面试官记不住技术清单，但会记住"你在哪里做了取舍"。

**1. LLM 不接触钱和权限**
扣费、权限、模型路由、导出参数全部是确定性代码；Agent 只上报 `estimated_cost` 与策略建议。
理由：生成式输出不可审计、不可复现，一旦让它决定扣费，账目必然出现无法解释的缺口。

**2. 一致性靠锚点，不靠 prompt 撞运气**
角色一致性以 `asset_id` 锚点条件图为准，配 QC 闭环（≥0.80 通过 / 0.68–0.80 警告重抽 / <0.68 失败），重抽≤3 轮后交人工判定。
理由：prompt 是"提高概率"，锚点是"约束结果"；这是产品能否交付的分水岭。

**3. 计费做成"冻结 - 结算 - 返还"三段式**
生成前按预估计冻结 → 按实际 token 结算 → 失败全额返还，全程流水可查，支付回调以 `out_trade_no` 幂等。
理由：一次性扣费在失败场景下必然引发客诉；冻结模型让"成本可预知"成为可承诺的产品能力。

**4. 实时通道选 SSE 而不是 WebSocket**
生成进度是单向推送，SSE 天然适配；带 `Last-Event-ID` 断线补偿 + 心跳，弱网/刷新后回放历史事件。
理由：WebSocket 的双向能力在这里是负担——要自己维护连接状态与重连协议。

**5. 主动给"图编排"划边界（ADR-09）**
只有编剧链路走 LangGraph；资产/分镜/渲染/后期/发行确认为同步管线（域服务 + 执行器重试 + 幂等键）。
理由：其余五条链路都是"单域内有限步骤、状态可由业务表完整表达"，图化的收益（跨节点恢复）低于改造成本。**这个决策是我主动砍掉的复杂度，不是做不完的妥协。**

补充一条工程细节（很能说明问题）：实测两家模型都是**推理模型**，小 `max_tokens` 时输出预算被 `reasoning_content` 吃光导致 `content` 为空。我在网关做了「空内容自适应重试」（`finish_reason=length` 且空内容时自动翻倍预算重试一次，上限 16000），并把 `reasoning_tokens` / `finish_reason` 落库计量。

## 八、个人贡献（讲"我做了什么"，而非"项目有什么"）

**1. 产品定义（从模糊想法到可开发需求）**
- 输出 PRD V4.0：8 个功能域、78 条用户故事、195 条 Given/When/Then 验收标准，全部下探到字段级（`final_prompt ≤ 500 字`、`duration_ms ∈ [1000,15000]`、字幕单句 ≤ 20 字）；
- 建立"痛点 → 方案 → 指标"追溯矩阵，北极星指标 CCCR + 7 个一级指标 + 6 个二级指标，避免功能做完无法验收；
- 明确 9 条非目标与三期路线（MVP / P1 团队协作 / P2 商业化），挡住范围蔓延。

**2. 架构与契约（先把边界定死）**
- 系统架构文档：C4 Context/Container 分层、模块划分、9 条 ADR（队列选型、主键策略、幂等键、HITL 实现、一致性方案、计费位置、模型路由、画布选型、编排路线）；
- 57 张表的 ER 图与数据字典，枚举/错误码/命名统一收敛到术语表作为唯一事实来源；
- 109 个接口的契约文档 + OpenAPI 导出，前后端并行开发不互相等待。

**3. 后端实现（确定性优先）**
- 计费：冻结/结算/返还全链路 + 幂等键三元组 + 支付回调幂等 + 超时解冻；
- 编排：编剧子图（大纲→逐集→审核→审批挂起/恢复），驳回反馈回流局部改写；
- 网关：双供应商接入、表驱动路由、成本记账、推理模型空内容自适应重试；
- 执行器：优先级队列、按用户并发配额、指数退避重试、崩溃恢复。

**4. 前端实现（把长流程变得可理解）**
- 24 页全量实现，五态视觉语义（生成中/待确认/已锁定/失败/拦截）统一到 `statusTone`；
- Konva 分镜画布：拖拽排序后重算时长与镜头序，交互帧率达标；

## 九、面试陈述脚本

**90 秒版（开场用）**

> 我做的是一个 AI 短剧创作工具，叫浮光造梦。它解决的问题不是"生成一段视频"，而是短剧生产链路上的六次返工：剧本到分镜靠人工翻译、角色跨镜头不一致、五六个工具之间手工搬文件、成本要到最贵的视频环节才发现错了、流程中断就得重来。

## 十、高频追问与答法

**Q1：媒体生成都是占位（Stub），这个项目算做完了吗？**
> 链路是完整的，供应商是占位的。剧本、审核、元数据走真实 DeepSeek/GLM；图像/视频/TTS/BGM 由 Stub Provider 生成占位文件，但**契约、成本记账、幂等、重试、QC 判定、权益校验、失败返还全部真实运行**。替换点收敛在 `model_gateway` 一层，加 Provider + 注册表即可切换。我没有假装它上线了，验收报告里把 Sandbox 边界单列成章。

**Q2：为什么不用 Redis / Celery / 消息队列？**
> 硬约束是"单机一键启停、无外部中间件"，所以队列语义自己实现：优先级入队、按用户并发配额、指数退避重试、进程重启后把未完成任务重置入队。**代价我也清楚**：只支持单实例，事件总线在进程内。所以架构文档写了生产化路径（Redis 队列 + 对象存储 + 多实例），并且明确这是 P2 收尾而不是"以后再说"。

**Q3：最难的坑是什么？**
> 网关的推理模型空输出。两家模型都会把 `max_tokens` 预算先花在 `reasoning_content` 上，小预算时 `content` 直接是空字符串，表现为"模型没说话"。我先做归因（把 `finish_reason` 和 `reasoning_tokens` 落库），再做自适应重试，最后把"重试期间遇到 HTTP 4xx 不能掩盖真实原因"这条也补上，否则上层会收到误导性错误。

**Q4：你怎么证明产品是成立的？**
> 诚实说：还没有真实用户规模，所以不宣称成立，只做到"可观测"。北极星是 7 天内创意到成片的完成率，配套埋点最小集已经上线——四关口一次通过率、导出漏斗都能出真实数字（当前样本是测试与 e2e 产生的，剧本关口 62.5%、资产 94.8%）。下一步是接真实模型后重标定 QC 阈值与成本基线。

**Q5：如果重做一次，你会改什么？**
> 两件事：一是埋点应该和功能同批交付，我是第二轮才补的，导致前期的指标只能倒推；二是五条链路的编排一开始就该明确"同步管线"，先图化再回退，浪费了一部分改造成本——这也让我后来养成"先写 ADR 再写代码"的习惯。
