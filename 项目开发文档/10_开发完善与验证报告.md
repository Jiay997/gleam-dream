### 2.2 关键发现与网关强化（`openai_compat.py`）

实测发现两家模型当前均为**推理模型**（输出 token 先被 `reasoning_content` 消耗），
由此引入三类稳定性风险并逐一强化：

| 风险 | 实测证据 | 强化措施 |
|---|---|---|
| 小 `max_tokens` 下全部预算被推理消耗 → `content` 为空 | `max_tokens=16` 时两家 content 均为空、reasoning_tokens=15/16 | **空内容自适应重试**：`finish_reason=length` 且空内容时自动翻倍 `max_tokens` 重试一次（上限 16000）；仍为空则 `ok=False` 并携带 finish_reason（供编剧节点自修循环感知） |
| 重试期配额类 HTTP 错误掩盖真实原因 | 自适应重试超模型上限返回 HTTP 400 | 重试收到 HTTP ≥ 400 时按「空内容 + 原始 finish_reason」上报，不误导上层 |
| 推理消耗不可观测 | reasoning_tokens 占输出预算 20–95% | `meta.reasoning_tokens` / `meta.finish_reason` 计量并落 `ai_call_logs` 快照 |

### 2.3 记账口径修复（迁移 `a7c1d2e94b05`）

## 六、性能验证（09 报告 7.2 P2 风险闭环）

### 6.1 工具

`backend/scripts/perf_smoke.py`：7 接口组 × 并发档位（1/5/20）× 8 秒真实 HTTP 负载，
输出 P50/P95/P99、RPS、错误率，并按 NFR 口径自动判定。

### 6.2 连接池调优（实测驱动）

首轮压测发现 c=20 档 DB 触点接口 P95 达 1.8–2.1s（默认 `pool_size=5 +
max_overflow=10` 排队）。将池容量参数化并调优（`DB_POOL_SIZE=20 /
DB_MAX_OVERFLOW=30`，默认即代码默认值）后：

| 指标 | 调优前（c=20 最差组） | 调优后（c=20 最差组） |
|---|---|---|
| 最差 P95 | 2073ms（projects_list） | **1135ms**（approvals_list） |
| 最差 P99 | 3340ms | 1247ms |
| 错误率 | 0% | 0% |

### 6.3 最终实测数据（后端 8101，全量 77 测试后基线）

**正常档位（c≤5，NFR-P1 硬判定口径）：全部达标 ✅**

| 接口组 | c=5 P95 | c=5 P99 | RPS | 错误率 |
|---|---|---|---|---|
| health | 107ms | 123ms | 63.0 | 0% |
| health_db | 152ms | 182ms | 46.0 | 0% |
| health_models | 141ms | 163ms | 48.5 | 0% |
| projects_list | 212ms | 512ms | 31.5 | 0% |
| billing/plans | 201ms | 263ms | 34.2 | 0% |
| approvals_list | 256ms | 370ms | 26.2 | 0% |
| analytics POST（写组） | 262ms | 285ms | 26.9 | 0% |

> NFR-P1 目标：非生成类接口 P95 ≤ 500ms / P99 ≤ 1.5s —— **实测最差 P95=262ms，余量 48%**。

**过载档位（c=20，单进程 asyncio 服务器 4 倍超订阅，观测不判定）**：
最差 P95=1135ms、全组 0% 错误、RPS 31–66 —— 无请求失败，退化有界。

**资源占用（perf 全程 2 秒粒度采样，119 样本）**：

| 指标 | 实测 |
|---|---|
| 后端进程工作集 | 均值 133.3 MB / 峰值 136.7 MB |
| CPU | ~72 CPU 秒 / 240s 窗口（单核约 30%） |

> 说明：单实例架构（进程内 EventBus / asyncio 执行器）为 09 报告已记录的已知边界，
> 水平扩容需 Redis + 对象存储生产化（03 文档已有方案，属 P2 工程收尾）。
