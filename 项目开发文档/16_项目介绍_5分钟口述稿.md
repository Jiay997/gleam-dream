## 第一部分 项目背景

**1、这个项目是什么。**

浮光造梦是一个面向短剧创作者的 AI 全流程创作平台，把「剧本、角色资产、分镜、视频、配音配乐、成片导出」做成一条在线流水线：一句话创意进去，成片出来。目标是把一部短剧，从多人协作几周压到一个人做几小时。

**2、它解决的痛点。**

1、**角色跨镜头漂移**（全体创作者）：用资产 ID 作为唯一参照，后续镜头都依据该 ID，不再靠提示词描述长相；质检分数 ≥0.80 通过，0.68–0.80 自动重新生成。

2、**成本不可控**（个人创作者、小工作室）：叙事错误要到最贵的视频渲染阶段才暴露；四道人工确认关口配合静帧草稿先行和冻结式计费，让错误在最省钱的环节就被拦住。

3、**工具链割裂**（单人团队）：剧本、图像、视频、剪辑分散在五六个软件中，文件全靠手工转存；八段流水线把整条流程串起来，资产与元数据在同一个项目内复用。

## 核心功能

**5、剧本生成：LangGraph 状态图 + checkpoint。**

我没有把它做成同步接口，而是在外面套了一层状态机：LangGraph 显式状态图，中断点做成 interrupt，审批单与挂起状态双写，线程 ID 就是项目 ID，状态落在 checkpoint，重启后凭一张审批单就能续跑。其余五条链路仍是同步管线。

**6、角色一致性：主形象锚点 + 质检闭环。**

提示词只能提高概率，锚点才能约束结果。技术上分三步：先规划角色、场景、道具；再生成主形象、三视图、表情集并锁成一个资产 ID；最后所有镜头都以它作为条件图，而不是重新描述长相。质检闭环是 0.80 通过、0.68 到 0.80 重抽，最多三轮后交人工。

**7、分镜画布：Konva 场景图 + 落库校验。**

一页要放上百个镜头卡片，DOM 拖拽在这个量级会掉帧，所以改用 Konva 的 Canvas 场景图，稳定 60 帧。镜头时长在数据库层就做了 1 到 15 秒的区间校验，拖拽结束自动重算镜序和总时长。

**8、批量渲染：asyncio 队列 + SSE 推送。**

任务层用 asyncio 自己实现队列：优先级入队、按用户并发配额、指数退避重试、重启后任务重新入队。通道层用 SSE 而不是 WebSocket，纯单向、自带断线补发。没引 Redis 和 Celery，因为硬约束是单机一键启停，代价是只支持单实例。

**3、应用场景。**

个人创作者：晚上有个点子，一句话出剧本、锁定角色，AI 拆完镜头在画布上调，先出静帧草稿确认叙事，再批量渲染、配音配乐、导出。小工作室：编剧改剧本、导演排镜头、运营看预算，资产和分镜都沉淀在同一个项目里。MCN：按月批量供给，用成本预估和冻结式计费提前卡住预算。

## 第二部分 核心功能与技术实现

**4、技术栈总览。**

一句话概括：前端一套画布、后端一栈异步、编排一张图、模型一层网关。前端是 Vue 3.4 加 TS 严格模式，分镜用 Konva；后端是 FastAPI 加 SQLAlchemy 2.0 异步、PostgreSQL；编排用 LangGraph，模型走统一网关接 DeepSeek 和 GLM。选型主逻辑三条：AI 调用都是长 IO，所以全链路异步；Agent 返回的是文本，所以出口都要过 Pydantic；生成不确定，所以钱和权限绝不交给模型。

**5、剧本生成：LangGraph 状态图 + checkpoint。**

剧本要跑大纲、逐集生成、审核、等人确认，中途几十分钟。所以我没有把它做成同步接口，而是在外面套了一层状态机：LangGraph 显式状态图，中断点做成 interrupt，审批单与挂起状态双写，线程 ID 就是项目 ID，状态落在 checkpoint，重启后凭一张审批单就能续跑。其余五条链路仍是同步管线。

**6、角色一致性：主形象锚点 + 质检闭环。**

提示词只能提高概率，锚点才能约束结果。技术上分三步：先规划角色、场景、道具，再生成主形象、三视图、表情集并锁成一个资产 ID，最后所有镜头都以它作为条件图，而不是重新描述长相。质检闭环是 0.80 通过、0.68 到 0.80 重抽，最多三轮后交人工。

**7、分镜画布：Konva 场景图 + 落库校验。**

**8、批量渲染：asyncio 队列 + SSE 推送。**

任务层用 asyncio 自己实现队列：优先级入队、按用户并发配额、指数退避重试、重启后任务重新入队。通道层用 SSE 而不是 WebSocket，纯单向、自带断线补发。没引 Redis 和 Celery，因为硬约束是单机一键启停，代价是只支持单实例。

**9、计费：冻结、结算、返还三段式。**

我没有让扣费跟着生成走，而是拆成三段：生成前按预估冻结，完成后按实际 token 结算，失败全额返还，支付回调按订单号幂等。再配草稿模式，用户在最便宜的环节发现错误，而不是账单出来之后。这是"成本可预知"从愿望变成承诺的转折点。

**10、合规与质量工程。**

合规上：剧本生成前做前置审核，越界内容不进模型；真人素材授权四步留痕；成片强制带 AI 标识。质量上：77 个用例覆盖计费、状态机、幂等、质检、渲染、导出，12 步端到端冒烟跑真实模型，非生成类接口最差 P95 是 262 毫秒，目标是 500 以内。

**11、一句话总结。**

这个项目给我最大的收获是：AI 创作产品真正的门槛不在"能不能生成"，而在"叙事错误会不会在最贵的那一步才被发现"。所以我做的不是更强的生成，而是把人的判断放在四次成本跃升之前，让用户先看对，再花钱。

## 口述提示

- 时间紧可略过第 7 条（分镜画布），保留第 5、6、8 条，它们是技术深度的主力。
- 第 6 条要讲慢一点：锚点和提示词的区别，是全稿最容易被记住、也最能体现工程判断力的一句。
- 被追问边界时的标准答案：媒体生成是 Stub（但契约、成本记账、幂等、重试、质检、失败返还全部真实运行，替换点在模型网关一层）；部署是单实例（队列在进程内，生产化路径已写进架构文档）；支付、短信、平台分发是沙箱。
- 被问最难的一次修复：两家模型都是推理模型，小预算会把 token 花在推理内容上，正文返回空字符串。我在网关把结束原因和推理 token 落库做归因，再做空内容自适应重试。
